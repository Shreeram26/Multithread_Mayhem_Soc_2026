# Week 6, Problem 1 — Trace the scheduler

**Process traced:** a freshly-forked child, from `allocproc()` through one full scheduling round-trip.
**Checkout used:** `mit-pdos/xv6-riscv` @ commit `79fa703ee1df7b548ef0bae4f834c453ac75319a` (2022-09-09), **plus my own Week 6, Problem 2 changes** to `scheduler()` (see `kernel-diffs.patch`) — checkpoints 3 and 7 below describe my modified version, not stock xv6, since that's the version I actually need to understand and defend.

---

## 1. Process creation

`allocproc()`, `kernel/proc.c` (lines 109–150). It finds a free slot by scanning the whole `proc[]` array from the start (line 114: `for(p = proc; p < &proc[NPROC]; p++)`), acquiring each slot's lock and checking `p->state == UNUSED` (line 116); the first `UNUSED` slot found is kept locked and used (`goto found`), every other slot it passed over along the way gets its lock released again (line 119) before moving on. At `found:` (line 124), it initializes: `pid` (via `allocpid()`), `state = USED`, and (after my Week 5/6 changes) `syscalls = 0` and `priority = 31`; then it allocates a trapframe page, builds an empty user page table, and sets up the initial kernel context (`context.ra = forkret`, `context.sp` = top of the kernel stack) so that the first time this process is ever scheduled, it starts executing at `forkret()` rather than in the middle of some unrelated function. `allocproc()` returns with `p->lock` **still held** — the caller (`fork()`) is expected to finish initializing the process and release the lock itself. The state right after `allocproc()` returns is `USED` — not yet `RUNNABLE`.

## 2. Becoming RUNNABLE

`fork()`, `kernel/proc.c` (line 296): `np->state = RUNNABLE;`, immediately followed by `release(&np->lock)` (line 297) — this is the very last thing `fork()` does before returning the new PID to the parent. It must hold `np->lock` during this transition because `p->state` is documented in `proc.h` as one of the fields protected by `p->lock` (line 88's comment) — without the lock, another CPU's `scheduler()` could observe a half-updated process (e.g. a state of `RUNNABLE` while some other field `fork()` is still writing hasn't been written yet), or two CPUs could race to both decide the same process is or isn't runnable.

## 3. The scheduler picks it up

`scheduler()`, `kernel/proc.c` (my Week 6 version — see `kernel-diffs.patch`). Each pass now does **two** scans rather than one: the first scan (my new lines, replacing the original single loop) walks the whole `proc[]` array, acquiring and releasing one `p->lock` at a time, looking for the `RUNNABLE` process with the smallest `p->priority` value — never holding two process locks at once, exactly like the original code's discipline for `p->state`. Once the best candidate is found, the second scan re-acquires **that specific process's** lock and re-checks `state == RUNNABLE` (it could have changed between the two scans, especially with more than one CPU) before actually doing anything. If it's still runnable: sets `state = RUNNING`, sets `c->proc = p`, and calls `swtch(&c->context, &p->context)` — all while holding `p->lock`. After the `swtch` call returns, `c->proc` is reset to `0` and the lock is released. If no process is `RUNNABLE` at all in a pass, the CPU executes `wfi` instead of spinning.

## 4. The context switch to the process

`kernel/swtch.S` (lines 9–40). `swtch(struct context *old, struct context *new)` saves the **current** callee-saved registers (`ra`, `sp`, `s0`–`s11` — 14 values in total) into `*old` (the scheduler's own `struct context`, `c->context`) using `sd` (store doubleword) instructions, then immediately loads that same set of registers back from `*new` (the target process's `p->context`) using `ld` instructions, and finally executes a plain `ret`. It restores absolutely nothing else — no `a0`–`a7`, no `t0`–`t6` — because `swtch` is only ever called from one very specific place (either the scheduler switching to a process, or a process calling `sched()` to switch back), and the C calling convention already guarantees the caller doesn't need any caller-saved registers to survive across a function call. `swtch` "knows" where to start executing in the new context purely because `ra` (the return address) is one of the 14 registers restored — loading a *different* saved `ra` into the register and then hitting `ret` is indistinguishable, from the CPU's point of view, from any other function returning to a different call site. For a brand-new process this `ra` was set by `allocproc()` to `forkret` (checkpoint 1); for a process resuming after a previous `sched()` call, it points back into the middle of `sched()` itself.

## 5. Running

While the process executes in user space, `c->context` (this CPU's `struct cpu`, specifically its saved `context`) just sits there, unused and unchanged — it's the frozen register snapshot of `scheduler()`'s own call stack at the exact moment it called `swtch`. `scheduler()` itself isn't "running" anywhere during this time; its execution is paused mid-function-call, parked in exactly the state `swtch` left it in, waiting for some future `swtch(&p->context, &c->context)` (note the argument order swap) to restore it and let it continue right after the original `swtch` call in `scheduler()`.

## 6. Yielding the CPU

A timer interrupt arrives while the process is in user mode, which traps through `uservec` into `usertrap()` (`kernel/trap.c`). Since this isn't a syscall (`r_scause() != 8`), it falls to the `devintr()` branch (line 69), which recognizes the timer interrupt and calls `clockintr()`, returning `2` (`which_dev == 2`, meaning "timer"). Back in `usertrap()`, line 84: `if(which_dev == 2) yield();`. `yield()` (`kernel/proc.c`, lines 487–495) acquires `p->lock`, sets `p->state = RUNNABLE` (not `SLEEPING` — this is a *voluntary* give-up, the process isn't blocked on anything, just done with its turn), and calls `sched()`. `sched()` (lines 466–484) does a few sanity `panic()` checks (that we're holding exactly `p->lock`, that `noff == 1`, that the state isn't `RUNNING` anymore, that interrupts are off), saves `mycpu()->intena`, and calls `swtch(&p->context, &mycpu()->context)` — the mirror image of checkpoint 4's call, switching **back** to whatever the scheduler's saved context was. When that `swtch` returns (inside `sched()`), it restores `mycpu()->intena` and returns to `yield()`, which then releases `p->lock` — but by then, execution is conceptually "back" wherever the corresponding `scheduler()` call originally invoked `swtch` from.

## 7. The scheduler picks another process

Back in (my Week 6) `scheduler()`, control resumes right after the `swtch(&c->context, &best->context)` call from checkpoint 3. It sets `c->proc = 0` and releases `best->lock` (my version's cleanup, equivalent to the original's `release(&p->lock)`), then the outer `for(;;)` loop begins its next pass: a fresh first scan over all of `proc[]`, acquiring/releasing one lock at a time, comparing `p->priority` among everything currently `RUNNABLE` — which now includes the process we just yielded from (since `yield()` set it back to `RUNNABLE` before calling `sched()`) alongside whatever else is runnable. Whichever process has the lowest `priority` value this time — which might be the same process again, if its priority is still numerically the lowest — gets picked for the next round.
